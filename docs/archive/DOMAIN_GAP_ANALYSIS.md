## EXECUTIVE SUMMARY

This **Domain Gap Analysis** provides a rigorous architectural audit of the 12 Canonical Domains established in `CANONICAL_DOMAIN_MODEL.md` and `DOMAIN_RELATIONSHIP_MATRIX.md`.

The purpose of this audit is to identify all remaining conceptual ambiguities, boundary overlaps, unassigned business logic, missing domain events, and technical edge cases. By explicitly documenting these gaps now, the system prevents unauthorized developer assumptions during Phase 4 (Technical Specification & Data Schemas).

---

## 1. AMBIGUITIES & BOUNDARY WEAKNESSES

### GAP-001: Boundary Overlap Between Learning Stage 4 ("Building") and Project Milestones
- **Location:** `DOM-001: Learning Domain` vs. `DOM-005: Project Domain`
- **Ambiguity:** Stage 4 of the 8-Stage Learning Lifecycle requires the user to "Build" a project deliverable. However, `DOM-005: Project Domain` also owns project instance management, milestone deliverables, and submissions.
- **Architectural Risk:** Risk of duplicate state tracking (e.g., both domains attempting to track whether a project milestone is active or completed).
- **Required Resolution for Phase 4:** Formally define that `DOM-005` owns the project deliverable instance state, while `DOM-001` treats the project milestone ID purely as an external completion reference for Stage 4.

### GAP-002: Memory Retention, Context Window Budgeting, and Summarization Logic Ownership
- **Location:** `DOM-002: Memory Domain` vs. `DOM-004: AI Core Domain`
- **Ambiguity:** Memory stores extensive historical records (mistakes, reflections, skill states). `DOM-004: AI Core` requires this context for reasoning, but LLM context windows are bounded. It is ambiguous which domain owns the summarization and context truncation algorithm.
- **Architectural Risk:** `DOM-004` attempting to manage memory database queries directly, or `DOM-002` delivering context payloads that exceed token budgets.
- **Required Resolution for Phase 4:** Assign `DOM-002` sole ownership of context budgeting and vector/keyword retrieval filters, delivering a pre-trimmed payload that strictly conforms to token constraints requested by `DOM-004`.

### GAP-003: Ownership of Socratic Conversation State vs. Review Critiques
- **Location:** `DOM-004: AI Core` vs. `DOM-009: Review Domain` vs. `DOM-007: Dashboard Domain`
- **Ambiguity:** When an AI review fails a submission, it issues a `DiagnosticCritique` and may initiate a Socratic dialogue. It is ambiguous where active dialogue thread state is stored.
- **Architectural Risk:** Unstructured chat logs leaking into Memory, violating the principle that Memory is not chat history.
- **Required Resolution for Phase 4:** Enforce that `DOM-004` manages transient dialogue state in memory buffers, and upon session termination, dispatches a synthesized `ReflectionSynthesized` or `MistakePatternDetected` event to `DOM-002` for structured archival.

## 2. UNASSIGNED BUSINESS LOGIC

### GAP-004: Temporal Skill Decay Formula
- **Unassigned Logic:** The principle dictates that skill confidence decays over time if unpracticed. The mathematical decay rate formula (e.g., exponential half-life, spaced repetition interval, time-since-last-artifact) is not yet assigned to a specific domain or configuration spec.
- **Target Assignment:** Must be assigned to `DOM-002: Memory Domain` as an asynchronous scheduled evaluation worker.

### GAP-005: Evaluation Rubric Construction & Versioning
- **Unassigned Logic:** `DOM-009: Review Domain` evaluates artifacts against `EvaluationRubric` objects. However, it is unspecified where rubrics originate (e.g., statically generated from `DOM-003: Knowledge Domain` or dynamically authored by `DOM-004: AI Core`).
- **Target Assignment:** Assign static rubric template definitions to `DOM-003: Knowledge Domain` for standard exercises, with dynamic context enrichment generated by `DOM-004: AI Core Domain`.

### GAP-006: Offline Submission Recovery & Artifact Hashing
- **Unassigned Logic:** If the single user works offline and completes practical exercises, it is unspecified how `DOM-011: Evidence Domain` handles local artifact hashing and timestamp synchronization upon reconnection.
- **Target Assignment:** Assign offline event queuing and local content-hashing logic to `DOM-011: Evidence Domain` client-side handlers.

## 4. TECHNICAL EDGE CASES & EXCEPTION SCENARIOS

### EDGE-001: AI Core Outage or Rate Limit During Stage Gate Review
- **Scenario:** The user completes Stage 5 ("Reflecting") and submits an artifact for Stage 6 ("Reviewing"), but the AI service (Gemini API) experiences a rate limit or timeout.
- **Required Behavior:** The system must transition the submission to `Pending Review` state in `DOM-009`, present a clear non-blocking message via `DOM-007`, and retry evaluation asynchronously. Bypassing the review or auto-approving is strictly illegal.

### EDGE-002: User Submits Identical Artifact for Multiple Exercises
- **Scenario:** User attempts to bypass practical work by submitting a previously approved artifact for a new exercise.
- **Required Behavior:** `DOM-011: Evidence Domain` detects identical content hash, flags an `ArtifactHashConflictDetected` event, and `DOM-009: Review Domain` automatically renders a `Revision Required` verdict citing unoriginal evidence.

### EDGE-003: Radical Career Target Change Mid-Path
- **Scenario:** User changes target career role from "Systems Engineer" to "AI Data Architect" in `DOM-010: Settings`.
- **Required Behavior:** `DOM-006: Career Domain` computes a new `CompetencyGap`, `DOM-001: Learning Domain` archives active unaligned paths, and generates a new macro trajectory. Previously verified skills in `DOM-002: Memory` remain intact.
